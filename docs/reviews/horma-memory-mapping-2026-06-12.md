# Part 1: Paper review

# HORMA: "Organize then Retrieve: Hierarchical Memory Navigation for Efficient Agents" — Full Technical Report

arXiv 2606.11680 (v1, submitted 2026-06-10). Hao-Lun Hsu, Nikki Lijing Kuang, Boyi Liu, Zhewei Yao, Yuxiong He (Duke + Snowflake AI Research). Source: full arXiv HTML (LaTeXML), read end-to-end including appendices A–E. No code repo link found in the paper.

**One-line summary:** HORMA = a frozen primary LLM agent + two tool-using helper agents sharing a bash-accessible hierarchical file-system memory workspace: a **memory manager** (M_m) that organizes raw trajectories into linked structured notes (improved offline via contrastive "textual gradient descent" on its prompt), and a **retrieval agent** (M_r) that navigates the workspace with `ls/grep/cd/cat` + `select/done` (optionally RL-trained with GRPO on a Jaccard evidence reward).

---

## 1. Memory-Augmented MDP formulation

- **M-MDP tuple:** `(S, O, A, T, R, F)` — citing [64] for "M-MDP". S/O/A standard; `T` = environment dynamics; `R` gives **binary task reward R_T ∈ {0,1} only at final step T** (sparse, terminal); `F_t` = external memory state at time t.
- **Memory workspace state:** F_t "consists of structured files and directories (e.g., entity logs, event summaries, state trackers)". It "persists externally and can scale with task complexity" — unbounded, unlike the context window W.
- **Memory transition (Eq. 2):**
  `F_{t+1} = T_F(F_t, a_t, o_t)`
  The paper explicitly rejects implementing T_F as hand-crafted heuristics ("fixed summarization or rule-based file updates... brittle"); instead T_F is **operationalized as an agentic management task** performed by M_m.
- **Decoupled policy factorization (unnumbered eq. after Eq. 2):**
  `π(a_t | o_t, F_t, q) = M_r(C_t | F_t, q) · M_θ(a_t | o_t, C_t, q; P_main)`
  where M*r selects context `C_t ⊆ F_t`; M*θ is the frozen primary LLM policy; q = task query; P*main = fixed prompting context (environment description, tool specs, output formats, few-shot demos). Baseline without memory is Eq. 1: `M*θ(a*t | o_t, H*{t-1}, q; P_main)` over raw history H.
- **Decoupling rationale:** "memory construction and memory retrieval operate at fundamentally different temporal and functional scales. Memory construction shapes the long-term structure of stored information and induces delayed effects on downstream reasoning, whereas retrieval directly affects per-step inference quality on the execution path." Hence: construction = no RL (delayed credit, sparse reward → "highly unstable"), retrieval = RL (localized behavioral feedback, on execution path). Conclusion frames it as "separating asynchronous memory organization from per-step retrieval... improves credit assignment."
- **Conversational extension:** H = (u*0, r_0, ..., u_T, r_T) (user/assistant turns); baseline Eq. 3 conditions on full H; HORMA uses `π(a|F,q) = M_r(C|F,q) · M*θ(a|C,q; P_main)`.

## 2. Memory CONSTRUCTION stage

- **Workspace structure (§4.2):** Hierarchical file system, not a flat buffer. Per interaction (a_t,o_t) or dialogue turn (u_t,r_t), M_m: (1) **archives the raw trajectory into a timestamped directory**; (2) **selectively synthesizes structured notes** based on task relevance. "Each synthesized note stores compact task-relevant abstractions together with temporal metadata and references to underlying raw trajectories" — i.e., provenance pointers enabling "efficient retrieval without sacrificing provenance or recoverability."
- **Concrete workspace example (Appendix E, LoCoMo, verbatim structure):** three note files shown —
  - `People/Caroline.md` — entity file with sections ("LGBTQ Support Group Attendance", "Career Plans"), each bullet carrying a turn-level provenance pointer like `(D1:3)`, `(D1:11)`.
  - `Dates/May2023.md` — temporal index: per-date bullets, again with `(D1:3)`, `(Session 1)` pointers, including session start time ("1:56 pm").
  - `Topics/LGBTQ/support group.md` — topic file with verbatim quotes: `"I went to a LGBTQ support group yesterday and it was so powerful." (D1:3)`.
    So the emergent schema is **multi-axis indexing: People/, Dates/, Topics/ directories, with the same fact cross-referenced under multiple paths and every claim anchored to dialogue-turn IDs.** (This redundancy is itself a learned skill — see "Retrieval Path Redundancy" below.) No full directory tree of the raw-trajectory archive is shown; the raw side is only described as timestamped directories.
- **Memory manager agent M_m (§4.3):** issues "executable file-system operations through Bash commands (e.g., `mkdir`, `nano`, `mv`)". Runs per interaction step / dialogue turn, asynchronously off the execution path. Backbone in main experiments: Claude Sonnet 4.5.
- **Initialization:** domain-agnostic prompt P_m^(0) specifying "high-level organizational principles such as entity tracking, event abstraction, and relation grouping." The full text of P_m^(0) is **not** given in the paper (vague spot).

## 3. Contrastive failure analysis / skill evolution ("Recursive Skill Refinement", §4.3)

- **Contrastive sets** (compare same task run with raw history H = unconstrained baseline vs managed context H' = HORMA):
  - **D_exo (exogenous):** H succeeds, H' fails → "information loss during memory construction" (facts never written, overwritten summaries, wrong file read, grep misses, truncation — per the D.5 prompt).
  - **D_end (endogenous):** H' succeeds, H fails → "structured memory mitigates issues such as hallucination or lost-in-the-middle effects."
- **Eq. 4:** `Feedback_i = LLM(Feedback Instruction, H, H')`
- **Eq. 5 (textual gradient descent, citing TextGrad [56]):**
  `P_m^(k+1) = LLM(Skill Augmentation Instruction, P_m^(k), {Feedback_i}_{i=1..n})`
  Yields "a growing library of domain-specific memory management skills (exogenous and endogenous)." The Skill Augmentation Instruction text itself is **not** printed (vague spot); the feedback-generation prompts ARE printed:
- **Prompt D.4 (Endogenous Skill Discovery), near-verbatim:** "You are an expert in contrastive analysis of interactive agents with different memory setups. EXPERIMENTAL SETTING... BASELINE simulates no practical context limit... OUR METHOD: an external memory folder updated and read via Bash (files, notes, summaries). The live policy prompt is not carrying the entire raw trace. Outcome here: OUR METHOD succeeded. BASELINE failed. [original memory management prompt] [Task ID / Category / Initial Observation / Success Trajectory / Failed Trajectory] YOUR JOB — ENDOGENOUS SKILLS (PRIMARY HYPOTHESIS): Your main hypothesis is that baseline failed because super-long raw history in context causes hallucination, lost-in-the-middle effects, or attention dilution... For each skill, tie it to why raw-history overload hurts and how OUR METHOD sidesteps it. Do not reduce this to generic 'better planning' unless you anchor it in context-length/memory-structure mechanisms."
- **Prompt D.5 (Exogenous):** symmetric, with "Outcome here: OUR METHOD failed. BASELINE succeeded... Your main hypothesis is information loss in the Bash-managed llm file pipeline, e.g., facts never written, overwritten summaries, wrong file read, grep misses, truncation... If the trace includes Bash/file/memory tool strings, use them as evidence."
- **Prompt D.6 (Skill Fields Specification) — output JSON schema, verbatim:**

  ```
  { "task_id": ..., "task_category": "...",
    "comparison_type": "endogenous" or "exogenous",
    "winning_method": "ours_llm_file" or "baseline_full_raw_history",
    "losing_method": ...,
    "hypothesis_alignment": ...,
    "divergence": { "first_divergence_step": <int or null>,
                    "summary": "<when trajectories diverge>" },
    "skills": [ { "skill_id": "end_001" or "exo_001",
                  "title": "<exactly three to five words>",
                  "principle": "<one or two sentences>",
                  "evidence": ...,
                  "how_to_reinforce/acquire": ...,
                  "memory_prompt_improvement": "1-3 sentences - how to change the memory-writer / extraction prompt or schema" } ],
    "root_cause_summary": "<2-4 sentences>" }
  ```

- **Example learned skills (Appendix C, Tables 9–11):**
  - ALFWorld endogenous: `end_001 Goal-Object Spatial Pinning` (write exact object location immediately, high-relevance tag), `end_002 Failed-Action Loop Detection` ("last 5 actions: same target, all failed" flag for the "Nothing happens" loop), `end_003 Multi-Step Plan Persistence` (a `task_progress` counter).
  - ALFWorld exogenous: `exo_001 Preserve Object Identity Chains` (never abstract "mug 1" → "a mug"; keep a persistent object registry mapping IDs → last-known location/state), `exo_002 Receptacle State Persistence` (open/closed state per container), `exo_003 Appliance Interaction Failure Detection` (distinguish placed/toggled/retrieved).
  - LoCoMo/LongMemEval (shared across both, evidence of cross-domain skill consistency): `Temporal Precision Anchoring` (exact dates + relative-time pre-computations, e.g. "'yesterday' relative to Session 6 = July 5, 2023"), `Verbatim Quote Preservation` (exact quotes + speaker + turn IDs to stop paraphrase drift/confabulation), `Retrieval Path Redundancy` (index facts by person/date/topic/keyword), `Negative Evidence Handling` / `Encode Negative Evidence Explicitly` (record what was NOT discussed so the agent can answer "not mentioned"), `Causal Chain Preservation`, `Cross-Reference Comparative Facts` (comparable timestamps in retrievable proximity, not siloed in purchases.md vs events.md), `Implement Retrieval Coverage Diagnostics` (metadata on files searched / match scores / coverage gaps to distinguish "not in memory" vs "in memory, not retrieved").
- **Skill library growth (Fig. 3e/2e):** starting from empty set, 63 skills after 4 refinement rounds on LongMemEval; performance improves monotonically with library size. Skill evolution also reduces retrieval LLM calls.
- **No algorithm pseudocode boxes exist anywhere in the paper** — the loop is specified only by Eqs. 4–5 and prose.

## 4. RETRIEVAL stage (§4.4)

- **Formulation:** retrieval = grounded sequential decision-making over executable file-system operations; "retrieval decisions lie directly on the execution path and admit localized behavioral feedback, making retrieval naturally amenable to sequential policy optimization." M_r exploits "directory hierarchy, temporal organization, and provenance metadata" — unlike similarity retrieval which "may retrieve temporally inconsistent or causally irrelevant information."
- **Action space:** Bash commands `ls`, `grep`, `cd`, `cat`, plus two terminal actions `{select, done}`. `select` adds verified content to C_t; `done` terminates once evidence suffices. Retrieval operates over the compact structured notes by default, "selectively expanding into raw interaction traces only when necessary" (via provenance pointers).
- **Primary agent then acts (Eq. 6):** `M_θ(a_t | o_t, C_t, q; P_main)`.
- **GRPO post-training** (citing DeepSeekMath-style GRPO [30]):
  - **Reward (Eq. 7):** `J(C_t, E) = |C_t ∩ E| / |C_t ∪ E|` — Jaccard between retrieved context and ground-truth evidence E. No auxiliary format/length rewards are mentioned anywhere (paper is silent — assume Jaccard only). The unit of the sets is not formally defined; given evidence E "is directly derived from the original dataset [LoCoMo]", E is almost certainly the LoCoMo evidence-turn annotations, so the sets are dialogue turns/notes (my inference — paper does not state it explicitly).
  - **Training data:** LoCoMo train split = first 7 of 10 conversations = 1,089 QA instances. Test = 519 QA from the remaining 3 conversations. Trained ONLY on LoCoMo; ALFWorld and LongMemEval are zero-shot for the RL retriever.
  - **Model:** the paper calls it **"Qwen 3.5 4B"** throughout (NOT "Qwen3-4B" as in the task prompt — note the discrepancy; treat the paper's naming as authoritative for citation, the intended model is the 4B Qwen).
  - **Hyperparameters (Table 8):** lr 1e-6; batch 64; mini-batch 16; rollouts per task G = 8; clip ratio 0.2; KL coef 0.01; entropy coef 0.001; rollout temperature 1.0; top-p 0.95; max response length 2048; **max interaction turns 10** (episode cap on the navigation episode). Hardware: 4× NVIDIA H200 for RL training; closed-model inference on CPU VM (Xeon Platinum 8488C, 48 cores).
  - **Learned behaviors claimed:** "hierarchical exploration, recovery from failed commands, and refinement of search trajectories."
  - Future-work line confirms training is **offline/evidence-based, not online interaction-driven**: "extend the current evidence-based retrieval training framework to fully online interaction-driven learning."

## 7. Stated limitations and failure modes

- **No explicit Limitations section.** What's stated or visible:
  1. **Construction needs frontier-scale LLMs** (§5.3 Memory Construction Bottleneck): small open models (Qwen 3.5 4B) cannot manage memory well, and a strong retriever can't rescue a bad workspace. Cost implication: every step/turn invokes a Sonnet-class memory manager (paper never reports manager-side token cost — only primary-agent input tokens; a real gap for anyone replicating "efficiency" claims).
  2. **Retrieval RL is offline, evidence-supervised:** requires ground-truth evidence annotations (LoCoMo's); future work = "fully online interaction-driven learning." No reward exists for domains without evidence labels.
  3. **Per-category failures visible in tables:** ALFWorld Cool 4.8% under Small budget (vs Truncation 23.8); LongMemEval SS-preference 13.3 (vs Acon 40.0); LoCoMo Adversarial 13.4 (vs Acon 16.4) — abstention/preference-style tasks are relatively weak.
  4. Skill libraries are domain-specific (refined per benchmark); the paper shows skills transfer between similar domains (LoCoMo↔LongMemEval share skills) but skill refinement requires running paired H-vs-H' rollouts per task, i.e., 2× evaluation cost during the refinement phase.

## Where the paper is vague / inaccessible detail

- **P_m^(0)** (the initial memory-manager prompt) and the **Skill Augmentation Instruction** (Eq. 5's instruction) are never printed — only the feedback/discovery prompts (D.4–D.6) and downstream agent prompts (D.1–D.3, D.7) are.
- No algorithm pseudocode anywhere.
- Jaccard set units (turns? note files? selected snippets?) undefined; E "directly derived from the original dataset" (LoCoMo evidence annotations).
- No GRPO format/penalty rewards mentioned; no training curves; no statement of how many GRPO steps/epochs.
- Raw-trajectory archive layout (the timestamped-directory side) never shown concretely — only the synthesized-note side (People/, Dates/, Topics/ with `(D1:3)`-style turn pointers).
- How many skill-refinement rounds were used for the headline ALFWorld/LoCoMo numbers is not stated (only LongMemEval's 4-round/63-skill curve).
- Whether the memory manager runs truly in parallel (latency hiding) or just "off the critical path" logically is asserted ("asynchronous") but not measured; no wall-clock latency numbers.
- Model naming: paper consistently says "Qwen 3.5 4B" (not Qwen3-4B); also uses Claude Sonnet 4.5, Claude 3.7 Sonnet, GPT-4.1, GPT-4o mini in the cross-backbone table.

## [SOUND] Turn-Level Evidence Pointers: anchor every extracted memory to event-journal seqs and session lines, with on-demand raw expansion

**Dimension:** construction · **Effort:** medium · **Impact:** high

**Paper mechanism.** HORMA §4.2: synthesized notes carry 'temporal metadata and references to underlying raw trajectories' (the (D1:3) turn pointers in Appendix E), giving 'efficient retrieval without sacrificing provenance or recoverability'; retrieval operates on compact notes 'selectively expanding into raw interaction traces only when necessary'. Also the learned skill 'Verbatim Quote Preservation' (exact quotes + turn IDs to stop paraphrase drift/confabulation).

**Targets.** src/memory/session-extractor.ts (ExtractedFact type + extraction prompt), src/memory/memory-schema.ts + src/memory/migrations.ts (new chunks column evidence_refs, migration v17), src/memory/manager.ts ingest path (~lines 2506-2558), src/infra/event-journal.ts (add query-by-(run_id,seq) read API to event_log), src/agents/tools/memory-tool.ts (new memory_expand tool or memory_get extension), src/memory/knowledge-graph.ts (recordBelief / evidence_chunk_ids so graph edges become resolvable to raw events).

**Design.** Give the extraction LLM a line/turn-numbered transcript and require per-fact citations (exactly HORMA's D1:3 trick), producing ExtractedFact.evidence: Array<{kind:'journal', runId, seq} | {kind:'session', path, line}>. Persist as chunks.evidence_refs JSON. A new memory_expand tool resolves refs: session refs reuse the existing remapChunkLines machinery (internal.ts:259-268); journal refs gunzip the exact event blob from event_log by (run_id, seq) — the PLAN-16 journal already stores the complete tool_call/tool_result/assistant stream but nothing in the memory store points into it. Bind to biology: the recall-before-claim interceptor and low GCCRF empowerment/certaintyDelta trigger mandatory raw expansion before confident assertions (verbatim evidence beats paraphrase under uncertainty), and high cortisol biases retrieval toward expanding evidence_refs (precision under stress). Dream reconsolidation gains a faithfulness check: when a chunk in its labile window is rewritten, re-verify the mutation against its raw evidence to prevent drift — HORMA's anti-confabulation mechanism applied to bitterbot's reconsolidation (labile_until, v9 migration). Dream insights (origin='dream') should also carry refs to their source chunk IDs so every memory is two hops from ground truth.

**Novelty vs existing.** Closest existing: chunks carry path/start_line/end_line for file-chunked content (sessions/\*.jsonl remap works), and graph edges have evidence_chunk_ids. But LLM-extracted facts and dream insights are paraphrases with NO turn-level anchor; provenance_chain stores actor IDs, not source pointers; and the PLAN-16 event journal (the true raw-trajectory store, src/infra/event-journal.ts:36-49) is completely disconnected from the memory store — no chunk references run_id/seq. HORMA shows the compact-note-plus-pointer pattern is what lets a 308-token retrieval beat 20K-token raw context without losing recoverability.

**Verifier reasoning.** I tried to reject this and could not. Every named file, line range, and claimed gap checks out on inspection. (1) Targets exist and behave as claimed: ExtractedFact (session-extractor.ts:24-30) carries no source pointers and the extraction prompt feeds an un-numbered flattened transcript; manager.ts inserts extracted facts with start_line=0/end_line=0, so LLM paraphrases are genuinely unanchored despite the schema having line columns; event-journal.ts:36-49 matches the cited schema and there are ZERO references to EventJournal/run_id anywhere in src/memory — the journal really is disconnected from the memory store; remapChunkLines is exactly at internal.ts:259-268; knowledge-graph.ts has recordBelief and evidence_chunk_ids; current schema version is 16 so v17 is correct. (2) No near-equivalent exists: expand_message only resolves progressive-compression truncation fingerprints from an in-memory cache; deep_recall is query-driven RLM exploration with no stored anchors; memory_get is restricted to MEMORY.md/memory/\*.md; grep for evidence_refs/memory_expand finds nothing. (3) Integration points are feasible: the migration runner trivially accepts v17; EventJournal.query already filters by runId+sinceSeq (an exact-lookup method is a small addition); the interceptor framework exposes certaintyDelta in its context (interceptor.ts:65) and recall-before-claim is a real builtin interceptor; reconsolidation.ts has the labile window for the faithfulness check; manager.ts:2541-2558 already wires evidence chunk IDs into KG edges, so extending to raw refs is natural. (4) Impact is plausible: paraphrase drift in extracted facts and dream-rewritten chunks is a real failure mode this system is exposed to (reconsolidation mutates chunks in the labile window with no ground-truth check today), and the compact-note-plus-pointer pattern directly addresses it. Minor design gaps noted in corrections, but they are underspecifications, not wrong integration points.

**Verifier corrections.**

Minor underspecifications, not blockers: (1) Journal-ref production is harder than stated — session extraction runs on flattened session transcript files, which carry no run*id/seq; line-numbering yields session refs directly, but journal refs require a separate session-line-to-event correlation (event_log's session_key column is the plausible join key; the design should specify this). (2) The event journal is a separate SQLite DB (~/.bitterbot/event-journal.sqlite) from the memory store, and deleteTask purges events on task purge — evidence_refs can dangle, so memory_expand must tolerate missing refs gracefully. (3) memory_get is currently path-restricted to MEMORY.md/memory/*.md; extending it to resolve sessions/\_.jsonl paths needs a path-traversal guard, so a new memory_expand tool is the cleaner option of the two proposed. (4) The exact-event read API addition is nearly redundant — EventJournal.query({runId, sinceSeq: seq-1, limit: 1}) on the global seq already gets one event; only a (run_id, run_seq) lookup is genuinely new. (5) Nit: chunks have both provenance_chain (v1) and provenance_dag (v2, peer skill lineage); the proposal's claim about actor IDs vs source pointers is directionally right but conflates the two columns.

## [SOUND] Abstraction-level summary nodes in the SAGE graph with coarse-to-fine traversal, built by a dream-engine 'graph abstraction' mode
