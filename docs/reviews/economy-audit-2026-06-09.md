# Bitterbot Skills Economy: Final Assessment

Bottom line: you have built roughly ten solid segments of a skill economy and zero complete loops. Inbound money works (proven x402 sale on Base mainnet). Outbound money to peers has never worked. The flagship auto-generation path throws its own output away. Most of the remaining gaps are wiring, not construction.

## 1. How skills are generated today (most real first)

1. **Hand-written / manual skills.** Fully wired. loadSkillsFromDir with precedence over bundled/managed/personal/project/workspace dirs (src/agents/skills/workspace.ts:156-206), frontmatter parsing for tier/interceptors (src/agents/skills/frontmatter.ts:228-255). This is the only path that reliably produces skills the agent actually loads.

2. **Agent-authored skills via skill_manage + SICA gate.** Fully wired. Tool registered (src/agents/bitterbot-tools.ts:229), every create/edit stages into skills-staging and synchronously runs the schema + injection + regression gate (src/agents/skills/skill-manage.ts:191-226, skill-gate.ts:103-160); promotion refuses unless gateStatus passed (skill-promote.ts:100-105). This is the best-engineered path in the system. It is agent-initiated only; nothing prompts the agent to use it after successful work.

3. **DB skill crystals.** Fully wired, but a parallel universe. SkillCrystallizer mints crystals from execution telemetry every consolidation tick (src/memory/manager.ts:1659-1666), dream mutation/research evolve them with a sandbox gate and Pareto budget (dream-engine.ts:1878-1899). These crystals never become SKILL.md files: the onSkillCrystallized callback only logs (manager.ts:3723-3732). Dream-evolved improvements are never written back to the skills the agent loads. Two worlds, no bridge.

4. **Dream interceptor harvest (PLAN-20).** Half real. Harvest runs by default (dream-types.ts:38), clusters intervention records, writes SKILL.md candidates to skills-staging (interceptor-harvest.ts:183-209), and the operator can promote them from the Guards UI. But promoted candidates are inert markdown: execution requires a hand-written TS module under builtin-interceptors/ (synthesize-interceptor-candidate.ts:239-244), and only 4 hand-written ones exist (builtin-interceptors/index.ts:24-27). Worse, the promote path (guards.ts:246-255) is a raw file copy that bypasses the SICA gate the other promotion path enforces, and the promoted skill is then advertised externally as executable (agent-card.ts:177-182) while being unable to run. This is a proposal generator, not a self-improvement loop.

5. **Skill Seekers.** Runs and then destroys its own output. The loop is on by default and triggered from dream cycles (manager.ts:3848, dream-engine.ts:1704-1736), does the scrape and LLM work, then routes every envelope through ingestSkill (skill-seekers-adapter.ts:491), where the default policy is "deny" (ingest.ts:80, reject at :83-85). The tmpDir is deleted in the finally block (adapter:533-538), so the result is irrecoverable. doctor-skills.ts:62 even assumes the default is "review", so the diagnostic tool lies about why this fails.

6. **Dead:** crystallizeSkill / skills.crystallize RPC has zero callers anywhere and no producer ever constructs a CrystallizationCandidate (server-methods/skills.ts:175-209; the reward>0.85 detection in crystallize.ts:4-6 does not exist). crystallizeViaPython targets a nonexistent ai-engine/ directory (crystallize.ts:114). The PLAN-15 A-MAC curator (runHeuristicCuratorPass/runFullCuratorPass, skill-curator.ts:115,245) has zero production call sites despite docs/memory/skills-pipeline.md:806 claiming it runs on the manager's schedule. The "successful tool chains crystallize into skills" story is currently fiction.

## 2. How skills are marketed today

**What works:**

- **P2P gossip push (outbound).** Manual publish from SkillEditor (SkillEditor.tsx:377 -> skills.publish -> orchestratorBridge.publishSkill) and auto-publish of dream crystals (skill-network-bridge.ts:626-631, default on). Signed, broadcast, real.
- **A2A agent card + x402 sell gate (code-complete).** The card advertises all skills with per-skill USDC prices from MarketplaceEconomics (a2a-http.ts:103-139, agent-card.ts:96-110); inbound payment verification is genuinely hard (x402-verify.ts:57-226, on-chain Transfer log, replay window); a real sale was proven in prod.
- **Algorithmic pricing.** refreshListings runs every consolidation over shared crystals with quality gates (marketplace-economics.ts:152-198, skill-pricing.ts:93-120).

**What is one-sided or fake:**

- **Selling is off.** payment.enabled defaults false (defaults.ts:526-527), your live config has no a2a block, and payment.ts:80-84 fails without a manually set x402 address. This node serves A2A tasks for free today. Earning is currently zero by configuration.
- **Receiving is off.** Default peers reject all gossip (ingestPolicy "deny", ingest.ts:80). You publish into a network that, at default config, discards everything. Marketing to an audience that cannot hear you.
- **The browse marketplace is a phantom.** marketplace.search/trending/recommendations/detail are registered (dream.ts:529-585) but have zero clients anywhere, and would return [] anyway: SkillMarketplace is never instantiated due to an init-order bug (ensureSkillNetworkBridge at manager.ts:430 checks peerReputationManager, which is created one line later at :431), and the marketplace_listed flag's only writer lives in server-marketplace.ts, a file imported nowhere. Dead three ways at once. There is no UI to browse, buy, or set a price for anything.
- **No discovery.** A buyer must know your URL out-of-band (a2a-client-tool.ts:74-77). Gossip carries an a2aEnabled boolean but no URL (wallet-discovery.ts:22-35). ERC-8004 registration is dead code (erc8004-identity.ts:184 has no callers) and off by default.
- **Telemetry listener with no sender.** Management nodes consume marketplace_sale signals (management-node-service.ts:350-366) that no code ever emits, and the handler itself is orphaned. Network economic intelligence is structurally zero.

## 4. Top recommendations, ordered by (loop-closing impact) / effort

1. **Flip the ingest default from "deny" to "review"** (ingest.ts:80). One line. Wires two existing things: makes Skill Seekers output survive (quarantined, not destroyed) and makes default peers able to receive published skills, unblocking the entire peer direction. Matches what doctor-skills.ts:62 already claims. Safe: review quarantines with verification and injection scanning; nothing auto-executes.

2. **Build the revenue dispatcher + address bridge.** Two pieces, both small, only valuable together. (a) ~25 lines after releaseHeldPayments() at manager.ts:1709: iterate getReleasedPayments, resolve address, walletService.sendUsdc, markPaymentProcessed/Failed. All three dead methods come alive; no schema change. (b) ~5 lines in the telemetry handler (server-startup.ts:~344): when a wallet_capability event arrives, also call peerReputation.updateWalletAddress(author_pubkey, address), bridging the live gossip into the table the queue reads. This converts the 70/20/10 split from fiction to fact and is the single biggest credibility item for the whole economy. Mostly "wire existing"; the dispatch loop is the only new code.

3. **Make selling one-flag (or zero-config).** In payment.ts:80, fall back to getLocalWalletCapability()?.address the way agent-card.ts:57 already does, so enabling payment needs only a2a.payment.enabled=true. Then set that on your own node. One line plus config. Without this, link 5 stays broken regardless of everything else.

4. **Record buyer-side purchases and pass the db to A2aClient.** Two small changes: insert a direction='purchase' row in executeTask after sendUsdc succeeds (a2a-client.ts:~234), and construct A2aClient with the marketplace db using the exact pattern a2a-status-tool.ts:454 already uses. Fixes three things at once: the inert $2/day spend guard (a real wallet-drain risk), the always-$0 spend reporting, and the starvation of demand-driven dreams, since analyzeOpportunities feeds on purchase rows. Pure wiring.

5. **Bridge listings to the browse layer and fix the init order.** Swap manager.ts lines 430-431 so peerReputationManager exists before the bridge guard, and have refreshListings also set chunks.marketplace_listed=1 for listed crystals (marketplace-economics.ts:~203). The four already-registered browse RPCs start returning the same skills the economics engine already prices. ~10 lines. A renderer Marketplace tab calling them is the follow-up "build new" item, but make the backend truthful first.

6. **Put the A2A URL in the existing gossip.** Add a2aUrl to WalletCapability (wallet-discovery.ts:22-35), include it in the 30-min advertise loop (server-startup.ts:372-385), and let a2a-client-tool resolve a peerId to a URL. Four small edits. This is the cheapest possible discovery directory and bridges the mesh to the paid marketplace without ERC-8004.

7. **Give crystallization a producer.** Add a "crystallize" action to skill_manage calling crystallizeSkill in-process, plus one system-prompt line telling the agent to invoke it after highly successful multi-step chains. ~50 lines. Activates the entire dormant crystallize.ts pipeline including its P2P publish, with the agent's own judgment as the reward signal. Also: aggregate execution metrics across stable_skill_id lineage in getSkillMetrics so dream mutations inherit their parent's track record and can actually pass the listing gate (one query change).

8. **Wire the curator and enforce the wallet daily limit.** Curator: one call to runFullCuratorPass at the end of the dream cycle via the existing openSkillLifecycleStore helper. Daily limit: sum tx-history.json in a checkDailyLimit inside wallet-service.ts, called from sendUsdc and payForResource, the single choke point all spend paths share. Both are hygiene/safety items that matter more the moment recommendations 1-4 turn real money on.

Also: delete the dead weight before it misleads you again: server-marketplace.ts (never imported, divergent duplicate), crystallizeViaPython, the trade action in wallet-tool (always throws, wallet-service.ts:331-333), and fix wallet.setConfig (server-methods/wallet.ts:212-241), which currently returns ok and persists nothing.

The honest summary: items 1-4 are about two days of work, nearly all of it connecting modules you have already built and tested, and they take you from "no loop exists" to "a configured pair of nodes can generate, publish, discover, sell, and actually pay contributors." Everything past that is polish on a loop that finally closes.
