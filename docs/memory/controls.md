# Your memory controls

The **Memory** page in the Control UI shows what your agent remembers and gives you the say over it.

## What you can do

- **Find** a memory by its text, newest first.
- **Read** it in full, with where it came from.
- **Correct it.** The new text becomes a new memory (new id, same metadata) that replaces the old one: it is searchable by keyword at once and re-embedded so it is found by meaning again. The old memory is forgotten with the cascade below, except that what still holds moves to the new one (see [Forget and edit cascade](#forget-and-edit-cascade)).
- **Forget it.** It is deleted from the memory table, the keyword index and the vector index together, and so is everything that rested only on it (facts, graph links, dream insights; see the cascade below). You can preview exactly what goes first. This cannot be undone, and it sticks: the agent will not learn the same memory again from the same conversation (see below for the limit). A memory indexed from a conversation can be forgotten too; the transcript itself is not edited.
- **Retire a settled fact.** Facts the agent treats as true without looking them up are listed separately. Retiring one stops that; it is kept in the fact's history. Your retire is final until you lift it: the agent cannot bring the same value back by extracting it again or pinning it itself. Only you can, with **Bring back** in the retired list (`memory.unretireFact`) or by pinning it again (`memory.pinFact`).
- **Pin a fact** (`memory.pinFact`): what you state outranks what the agent pinned or learned, and brings back a fact you had retired.
- **Remove a learned preference** (what the agent has picked up about how you like things). It will not be learned again from the same wording or a close paraphrase.
- **Export everything** (export version 2): to a JSON file in `~/.bitterbot/exports/` (0600), or as a download to your browser. See [Export and import](#export-and-import).
- **Import an export** (yours, or from another install) back into memory, with a dry run first.

Over the gateway: `memory.list`, `memory.get`, `memory.facts` (with `status: "active" | "retired" | "all"`), `memory.preferences` and `memory.forgetPreview` need read access; `memory.edit`, `memory.forget`, `memory.retireFact`, `memory.unretireFact`, `memory.pinFact`, `memory.forgetPreference`, `memory.export`, `memory.exportDownload` and `memory.import` need admin. An operator without scopes (a guest) and a node get none of them. The CLI has `bitterbot memory forget`, `edit`, `export` and `import` ([CLI reference](/cli/memory)); `bitterbot gateway call` reaches every RPC.

```bash
bitterbot gateway call memory.list --params '{"q":"coffee"}'
bitterbot gateway call memory.forgetPreview --params '{"id":"fact_..."}'
bitterbot gateway call memory.forget --params '{"id":"fact_...","planHash":"<from the preview>"}'
bitterbot gateway call memory.facts --params '{"status":"retired"}'
bitterbot gateway call memory.retireFact --params '{"key":"infra.deploy_endpoint"}'
bitterbot gateway call memory.unretireFact --params '{"key":"infra.deploy_endpoint"}'
bitterbot gateway call memory.pinFact --params '{"key":"infra.deploy_endpoint","value":"api2.acme.com"}'
bitterbot gateway call memory.export
bitterbot gateway call memory.exportDownload
bitterbot gateway call memory.import --params '{"data":{...the export...},"dryRun":true}'
bitterbot gateway call memory.import --params '{"data":{...},"keepOwnerTier":true,"confirmOwnerTierGrantsHash":"<from the dry run>"}'
```

## Teach it once: corrections captured as you chat

You should not have to open the Memory page to correct your agent. When you say "no, the deploy endpoint is api2.acme.com", "always use the client's timezone for Acme reports" or "call me Vic" in a direct chat, the fact is in the ledger at your authority before the next turn, and the reply tells you so.

How it works, per turn, in order:

1. **A pre-filter** looks at your own words (the message you sent, not the quoted, replied-to, forwarded or thread-history text a channel attaches to it) for a corrective or standing-instruction shape. The list is the cost policy: a message without one of these shapes costs nothing and is left to the dream-time extractor. The shapes: `No,` / `Nope.` / `Wrong:` at the start of a sentence or line; `X is not Y` / `isn't`; `actually` followed by a fact ("actually the repo is ..."), never a plan change ("actually, let's ..."); `always` / `never` as an instruction (sentence-initial, after "please" / "you should" / "from now on", or followed by a verb such as use, reply, deploy), never as a description ("it's always sunny"); `from now on`; `remember that/this/to/my ...`, never "remember what/when" or "do you remember"; `it's X not Y`; `use X instead` / `instead of`; `I prefer X over/instead of/not Y`; `call me`; `my <identity or preference noun> is` (name, timezone, email, editor, repo, endpoint, ...) or `my X is <a name, URL, handle or number>`; `everywhere` / `globally` / `for all projects`. Code blocks, inline code, quoted lines (`> ...`), `[Replying to]` / `[Quoting]` / `[Forwarded from]` blocks, inbound metadata, thread history, the untrusted-context block and fetched content are all stripped first, so none of them can trigger a call or speak as you.
2. **One cheap model call** (the extraction model, `memory.extraction.model`, else the dream model) reads your words and the reply and returns up to five key/value facts, each flagged as a correction or not, with a scope hint. Never more than one call per message, recorded in the usage ledger as `memory/correction`; the call is cancelled (not just abandoned) if it has not answered within 12 seconds, and `usage.budgets.mode: "enforce"` pauses it like the other background lanes.
3. **The pin.** A fact is written at your tier (`owner`) only when the model called it a correction **and** the value appears in your own words as a whole token, outside a negation: in "no, not api2, it's api3" only `api3` can reach your tier. Anything else is written at the `extraction` tier, which cannot replace what you or the agent pinned deliberately. Values that look like credentials (API keys, tokens, bearer headers, private keys, JWTs, long hex) and keys named token/secret/password/api key are never stored, from any source, and never echoed. The evidence stored on the fact is the line of the conversation you said it on (`session:<file>#L<n>`). If the agent had pinned the same value itself during the turn (`memory_pin`), your words raise that fact to your tier; the agent's `evidence` field never does.
4. **The confirmation line.** The reply ends with one system-generated line, never written by the model, built from what was actually written: `Memory updated: deploy endpoint = api2.acme.com (was api.acme.com)`. It also covers what the agent pinned itself during the turn and what was held (below). In a group or channel chat it carries counts only, never values. A message you send while the agent is still answering (steered into that turn) or that waits in the queue is captured when its turn completes, and the line is sent on its own when there is no reply text to append it to.

What is held: when the agent's own `memory_pin` would replace **or retire** a fact that you or it pinned earlier (trust tier 2 or higher), nothing is written. The attempt is recorded as a `pending_supersede` or `pending_retire` conflict, the line says `held for your confirmation: deploy endpoint api.acme.com -> api9.acme.com` (or `retire deploy endpoint (api.acme.com)`), and the next open-question sweep asks you which value is current. Retiring and re-pinning cannot walk around the hold: a fact the agent or you pinned keeps guarding its key against the agent even once retired by decay. Your answer to the question, when it is one of the two values offered, is written at your tier and settles the question; so does restating the value in chat or pinning it with `memory.pinFact`. Any write at your tier closes the held attempts and open questions for that key. Diff-before-confirm with one-tap apply and revert are the next phase.

Where a fact applies (`scope`): `global` (the default), `project:<name>` or `person:<name>`. A project-scoped fact is injected into the agent's prompt only when the active project matches; the project is the name of the agent's workspace folder (`agents.list[].workspace`), and the shared default workspace counts as no project, so project facts never leak into it. Person-scoped facts are injected everywhere for now. A correction keeps the scope of the fact it replaces and a new fact is global unless you name the active project ("for Acme", with Acme being the workspace) or a person; a project the model names on its own, a project other than the active one, or a project when none is active all read as global, so a fact can never be written where nothing will ever show it. This is a deliberate deviation from the plan's "default to the current project" (PLAN-55 §3.2): on an install with one workspace there is no project to default to. When the line says `scope acme; say "everywhere" to apply to all`, saying "everywhere" (or "globally") in your next message re-pins that value as global at your tier. The Memory page shows the scope as a chip next to the fact; `memory.facts` returns `scope` and `evidenceRef`; `memory.pinFact` accepts `scope` and `evidence`; the agent's `memory_pin` accepts a project scope only for the active project.

Not captured: heartbeats, cron and scheduled runs, subagents, A2A tasks, circles, webhook sessions, group and channel chats, and anyone who is not you. The dream-time extractor still learns from those transcripts under its own first-party rules.

Switches:

| Key                         | Default | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `memory.correction.enabled` | `true`  | `false` stops the per-turn pass. Corrections then reach the ledger only through the agent's `memory_pin` or the dream-time extractor.                                                                                                                                                                                                                                                                                                                                                                                              |
| `memory.correction.confirm` | `true`  | `false` keeps the writes but drops the "Memory updated" line.                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `session.memory`            | `"on"`  | `"off"` is incognito for the background learners: transcripts are not indexed into memory, the session extractor does not read them, and corrections are not captured. Replies still work. It does **not** stop what the agent writes on purpose during a turn: `memory_pin`, `working_memory_note`, the pre-compaction memory flush to `memory/*.md`, or compaction summaries in the session. The transcript is still written to disk; set it back to `"on"` or run a reindex and those conversations are indexed like any other. |

## What sticks, and who can undo it

Your decisions outrank the agent's. Every fact in the ledger carries who wrote it, and a higher tier is never overwritten by a lower one:

| Tier | Source                           | Who writes it                                                                                                     |
| ---- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 3    | `owner` (alias `user_directive`) | You: `memory.pinFact`, and a correction you state in chat (the Memory page's Retire and Bring back use this tier) |
| 2    | `agent_pin`                      | The agent's `memory_pin` tool (replacing or retiring a tier 2+ fact is held for you)                              |
| 1    | `extraction`, `seed`             | Session extraction, the first-boot seed                                                                           |
| 0    | `promotion`, `web_research`      | Dream promotion, curiosity research                                                                               |

When something is retired, what brings it back depends on who retired it:

| Retired by                                                | Status          | Same value pinned again by extraction, promotion or the agent                        | `memory.pinFact` (you) | Bring back / `memory.unretireFact` (you) |
| --------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------ | ---------------------- | ---------------------------------------- |
| You: Retire on the Memory page, `memory.retireFact`       | `owner_retired` | Refused, logged as an `owner_retired` conflict, never turned into a question for you | Reactivates it         | Reactivates it                           |
| The agent: `memory_pin retire`                            | `retired`       | Reactivates it                                                                       | Reactivates it         | Reactivates it                           |
| Decay (90 days unconfirmed), hygiene or the ledger's cap  | `retired`       | Reactivates it                                                                       | Reactivates it         | Reactivates it                           |
| The staleness check (three unanswered "still true?" asks) | `unconfirmed`   | Reactivates it                                                                       | Reactivates it         | Reactivates it                           |

A retired fact is not a current belief: a different value for the same key is accepted from any source (it replaces the retired row, which stays in the history as superseded, and there is then nothing to bring back), and the agent is never asked "which is current?" about a key whose fact is retired. Only the exact value you retired stays out.

Behind this is a small table, `memory_suppressions`, that records what you removed. Session extraction, preference extraction, curiosity research and dream insight promotion check it before writing, and the ledger checks it before any pin below your tier. Each entry is recorded in the same transaction as the removal, so a memory is never gone without the record that keeps it gone. What each kind matches:

- **A forgotten memory**: its text, compared after lowercasing and dropping punctuation and spacing, so the same sentence re-extracted with different capitalisation, commas or a missing full stop still matches. A materially reworded memory is a different memory and can come back. If you corrected a memory before forgetting it, both the original and the corrected text are covered. A short passage forgotten from a conversation (under 40 characters or 5 distinct words after that normalisation, such as "ok, thanks!") is matched in that conversation's transcript only, so the same words in your other conversations are still indexed.
- **A retired fact**: the exact key and value (case and spacing aside).
- **A removed preference**: its key, and its value compared the same way as memory text; a restatement that the agent would have merged into the removed preference (the same word-overlap test it uses for duplicates) is skipped too.

`memory.unretireFact` and `memory.pinFact` lift a fact's entry; a forgotten memory's entry stays until a later release adds un-forget.

## When a fact changes, what repeated it follows

A correction is not finished when the ledger has the new value: older memories, your learned preferences, the knowledge graph, the agent's prepared answers, open tasks and `MEMORY.md` may still say the old one. Every ledger change (a new value replacing an old one, a retire, a bring-back, a retired value restated) is announced as a `canonical:changed` event with the key, old and new value, the writer's tier, scope and evidence. A queue picks it up after the write has committed, never inside your chat turn, and hands it to six followers in turn. Each one does a bounded amount of work, pauses between batches so the gateway stays responsive, can run twice without doing anything twice, and logs its own failure without stopping the others. A write that was rolled back propagates nothing.

What counts as a change worth following: a value replaced by another, and your own retire. A retire by the agent, by decay or by hygiene means "stop showing this", not "this is wrong", so nothing else is touched. A value coming back (you pin the old value again, or Bring back) undoes the marks and flags below and restores what the followers removed: the preference row comes back and closed graph links reopen (replacement links close).

**What "states the old value" means.** Every follower uses the same test. The old value must appear as a whole identifier: letters, digits, `_` and `$` are part of a word, and so are `.` and `-` between two word characters, so "Max" does not match `max_tokens`, `Math.max` or `Max-like`, and "api.acme.com" does not match "api2.acme.com" or "staging.api.acme.com". A value with a capital letter is matched with its case ("Max" the dog is not "max" the setting); an all-lowercase value ignores case. The text must also name what the key is about: one of the key's words other than generic and category words such as `user`, `project` or `identity` (`pet.dog.name` needs "pet", "dog" or "name"; `user.home_city` needs "home" or "city"). A memory the old fact was learned from (its evidence) counts without that word. Text that also states the new value describes the change and is left alone. Values under three characters, numbers up to four digits and words like "yes" or "none" never match.

| Follower         | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Search           | Matching memories are marked superseded (at most 200 per change, newest first). Your `memory_search` and `deep_recall` still return them, after every current result (current results fill the result slots first), at half their score, with the snippet starting `[superseded] (infra.deploy_endpoint is now "api2.acme.com")`. A guest's search never shows the tag, the current value or a changed ranking. With `memory.canonicalLedger.enabled: false` no marks are applied.                                                                                                                                                                                                                                              |
| Preferences      | The learned preference that mirrors the key (`<category>.<key>`, with `.`, `_` and `-` treated alike: `identity/user_name` is `identity.user.name`) takes the new value; your retire removes it if it still holds the retired value. No preference is ever created this way, and a value or key you removed as a preference is deleted instead of written back.                                                                                                                                                                                                                                                                                                                                                                 |
| Knowledge graph  | A current link at the old value whose relation is the one the key describes is closed with the graph's own `supersede` step, which keeps it in the belief history. The key decides the relation through a short fixed list (`employer` is `works_at` / `works_for` / `works_on`, `home_city` is `lives_in`, `language` is `uses`, `spouse` is `spouse_of`, ...) or by naming a relation directly; a key that names its own subject (`project.bitterbot.language`) only touches links from that subject. On a value change a link to the new value replaces it; on your retire nothing does.                                                                                                                                     |
| Briefs and tasks | Prepared answers the agent has not used yet (anticipation briefs) that state the old value are set aside (`stale_fact`) and never voiced; a brief set aside for two corrections comes back only when both are undone. Open tasks whose goal, done criteria, plan steps or latest handoff state it get a `staleFacts` entry, which `task_get` returns. When anything was flagged you get one question in the usual place for questions to you, for example: "Your correction: you changed infra.deploy_endpoint from "api.acme.com" to "api2.acme.com", but 1 open task(s) still rely on the old value. Should I update them? If you say yes I will rewrite them to use "api2.acme.com"; if not, I will leave them as they are." |
| Dream insights   | Insights that state the old value or were drawn from memories just marked superseded are flagged and never promoted into searchable memory. The same holds for an insight drawn from a memory you forgot.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `MEMORY.md`      | The next dream rewrite is given the current ledger values and the last ten corrections and retires (old -> new), with the instruction never to restate an old value as current.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

**Scope.** A `global` (or `person:`) fact propagates as above. A `project:<name>` fact never changes your preferences or the knowledge graph (both are global) and never flags tasks (a task is not tied to a workspace); it marks memories, briefs and insights only in the memory of the agent whose workspace is that project, and touches nothing elsewhere.

**Nothing is lost on a restart.** Each change is also written to a small outbox in the same transaction as the change itself. When the followers have run, the entry is stamped. A minute after the gateway starts, and every 30 minutes after that, entries that were never stamped (the gateway stopped first, or a burst of changes overflowed the queue) are run again, and supersession marks on memories that no longer exist are deleted. The outbox starts empty when this release first runs: corrections you made before it are not propagated retroactively.

Your own words in `MEMORY.md` stay yours. Wrap any part of it in owner markers and the dream rewrite keeps it character for character, in the section it was in:

```markdown
## The Bond (Theory of Mind)

<!-- owner -->

Call me Vic. Never schedule anything before 10am.
<!-- /owner -->
```

A label is allowed (`<!-- owner:schedule -->`), and the same block may appear more than once. If a rewrite drops or edits a marked block it is put back from the previous version, and an owner block that was not in the previous version is removed, on every rewrite including the very first one. The agent's own tools are held to the same rule: when a tool call (writing or editing the file, applying a patch, a shell command) adds, removes or changes an owner block, the owner blocks are put back exactly as they were, the rest of the change stays, and the tool result says so. Your own edits through the Control UI's file editor are kept as you saved them.

Not covered yet: memories indexed after the change are not checked against older corrections, and the confirmation line does not count what was propagated.

## Forget and edit cascade

A memory is rarely alone. Facts in the ledger cite it as evidence, knowledge-graph links cite it, dream insights were drawn from it (and some were promoted into searchable memories of their own), a curiosity finding may have become it, a learned preference may cite it. Forgetting it takes those with it, by these rules:

| What rests on the memory                                  | What a forget does                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A fact whose evidence is now empty                        | Retired, reason `evidence_removed`. Never deleted: it stays in the fact's history. A retire like this is soft: the same fact learned again from somewhere else comes back. If the fact was pinned again between the preview and the apply (by you or anyone), that newer row is left alone and listed as `retireSkipped`. |
| A fact at your tier (`owner`) whose evidence is now empty | Kept active and **listed** in the preview and the result, so you decide. Only its evidence id is removed.                                                                                                                                                                                                                 |
| A fact with other evidence still there                    | Kept; only the forgotten id is removed. A line reference into a conversation that still exists (`session:<file>#L<n>`) counts as evidence, and so does any other evidence reference (a URL, a quote).                                                                                                                     |
| A knowledge-graph link left with no evidence              | Closed (`valid_until` set), kept in the graph's belief history with the action `evidence_removed`. A link with other evidence only loses the id.                                                                                                                                                                          |
| A dream insight drawn from the memory                     | Flagged (`stale_fact`), so it is never promoted. A promoted insight memory (`dream_insight_*`) made from it, or citing the forgotten memory directly, is forgotten too and its text suppressed.                                                                                                                           |
| A curiosity finding that became the memory                | Its link to the memory is cleared.                                                                                                                                                                                                                                                                                        |
| A learned preference citing the memory                    | The id is removed from its evidence. The preference stays (remove it separately if you want it gone).                                                                                                                                                                                                                     |
| Dream-utility rows counting the memory                    | Deleted.                                                                                                                                                                                                                                                                                                                  |

Every fact the cascade retires goes through the ledger, so the followers described above run for it as they do for your own retire (older memories stating the value are marked superseded, the mirrored preference is removed, matching graph links close).

**Edit** is a forget plus a new memory. What still holds in the new text moves to the new memory instead of going: a fact whose value is still in the new text (whole words, case and punctuation aside), a graph link whose two names both are, a curiosity finding, a preference's evidence. Everything else follows the forget rules. The old text is suppressed, so extraction does not bring it back. An edit that changes only case, spacing or punctuation is refused (the old text's suppression would cover the new one). The edited memory keeps the conversation it was extracted from as its source, but it is yours now: deleting that conversation later does not forget it.

**Preview, then confirm.** `memory.forgetPreview` (read access) returns what would change: counts, the facts that would be retired, your facts that would be kept and listed, facts kept on other evidence, facts that would move to the edited text, graph links closed, insights flagged, and a `planHash`. With `text` it previews an edit (and returns the new memory's id). `memory.forget` and `memory.edit` take `preview: true` to do the same, and `planHash` to apply exactly what was previewed: if anything changed in between (something new now rests on the memory, say), the call is refused with "Preview again" and nothing changes.

**One transaction.** A forget or an edit of one memory is applied in one transaction with the deletion, the suppression and the audit entry: all of it or none. A plan with more than 500 writes (a deleted conversation with hundreds of memories) is applied in ordered batches, one transaction each, with the derived rows first and the memory deletions last, pausing between batches so the gateway stays responsive; if a batch fails, running it again picks up what is left (without flagging an insight twice). Working out the plan reads the database in windows of 1,000 rows with a pause after each. Previews run outside the memory maintenance lock, so at most two run at a time; a third is refused with "try again in a moment".

The audit log records the forget with the counts of what the cascade changed and the plan hash, never the text.

## Deleting a conversation

When a conversation is deleted (the Control UI's delete, or `sessions.delete` with the default `deleteTranscript: true`), what was learned only from it goes with it: its indexed memories, the memories extracted from it, and, through the cascade, facts whose only evidence was that conversation (its memories, or a line reference into its transcript). Facts at your tier are never retired; facts that survive are returned in the result as `memory.survivors`, each with the reason (`owner`, or `other_evidence`). `sessions.delete` waits up to 4 seconds for this; if the memory system is busy (a dream cycle holds its lock) the result says `pending` and the cascade finishes on its own. No text suppression is written: the transcript is gone, so nothing extracts it again, and restoring the file on purpose brings its memories back.

The cascade runs only for a transcript the delete actually moved away (its archived copy exists and the original path is gone). If the move fails, the transcript, its memories and the facts resting on them all stay, and the conversation can be deleted again.

**Who deleted it matters.** A delete you make (the Control UI, the CLI, any `sessions.delete` call without `initiator`) retires those facts with reason `evidence_removed`, which spreads like your own retire: the learned preference still holding the value is removed and older memories stating it are marked superseded. Automatic housekeeping passes `initiator: "system"`: the subagent cleanup (`cleanup: "delete"` and the archive sweep after `archiveAfterMinutes`) and `bitterbot doctor`'s probe cleanup. A system delete still forgets the conversation's memories and retires the facts resting only on it, with reason `evidence_removed_system`, but that spreads like the agent's own retire (nothing else is touched), and it never writes a suppression. Facts at your tier are never retired by either. The audit entry is `owner_forget_session` or `system_forget_session`.

It does not run on a session reset (the transcript is archived, not deleted), on session store retention pruning (which removes index entries, not transcripts), or when the memory index drops the chunks of a transcript that disappeared from disk (a moved or unreadable sessions folder looks the same, and must not retire every fact).

## Export and import

The export (version 2) is one JSON document with everything an owner needs to move or audit the agent's memory:

- `memories`: every memory with its metadata (`id`, `kind`, `source`, `path`, `semanticType`, `lifecycle`, `importance`, `createdAt`, `updatedAt`, `text`, plus `lifecycleState`, `origin`, `epistemicLayer`, `evidenceRefs`, `version`, `sessionTrust`, `sensitivity`), no embeddings;
- `facts`: every row of the facts ledger, all statuses, with the full history and evidence;
- `preferences` (with their evidence), `knowledgeGraph` (`entities`, `relationships`, `beliefHistory`), `dreamInsights`, `curiosityFindings`, `conflicts`, `directives` (the agent's open questions), `suppressions`, `auditLog`, `chunkSupersessions`;
- `workingMemory` (`MEMORY.md`) and `genome` (`GENOME.md`);
- `version: 2`, `format: "bitterbot-memory-export"`, and `redactions`.

A reader of version 1 still works: every version 1 field keeps its name and shape. What is never in it: `.env`, keys, wallet material, auth profiles or any file other than `MEMORY.md` and `GENOME.md` (the exporter reads only the memory database and those two files). Credential-shaped values are redacted by pattern (API keys, tokens, bearer headers, private key blocks, JWTs, long hex runs, long random base64 runs, card numbers): each is replaced with `[redacted]` wherever it appears, and `redactions` counts how many times. A long run made of words, such as a file path or a CamelCase identifier, is not a credential and is kept. A secret that matches none of the patterns is not caught.

**Getting it.** `memory.export` writes it to `~/.bitterbot/exports/memory-<time>.json` (0600) on the gateway's machine. `memory.exportDownload` returns a one-time link (`url`, valid for five minutes, usable once, under the Control UI's `basePath` when one is set) that streams the same document to the client as a download, page by page, never held whole in memory, and `sqlitePath`, the path of the raw memory database for when you want the file itself. `bitterbot memory export` writes the file (or stdout with `--out -`). An export reads the database page by page while the agent keeps working; if a reindex rebuilds the database in the middle, the export stops with "rebuilt during the export" instead of finishing from the old copy. Export again.

**Import.** `memory.import` (admin) and `bitterbot memory import <file>` restore an export of either version. `dryRun: true` (`--dry-run`) returns the counts and writes nothing. The rules, in order:

1. Only the agent's own memories are restored (facts, notes, insights and the rest). Memories indexed from files or conversations are skipped and counted as `fileBacked`: copy the files and reindex for those. Forgotten and expired ones are skipped.
2. Your suppressions on this install win: a memory, fact or preference you removed here is skipped and counted as `suppressed`. Importing never lifts a suppression, and a suppressed value is not restored as history either: history rows of a new key that you suppressed, that look like credentials or that hold `[redacted]` are dropped (`historyDropped`).
3. Duplicates are skipped: a memory whose id or exact text is already here, a fact whose key already holds the same value, a preference already learned.
4. Trust tier: imported facts are written with source `import`, the same tier as extraction (1). By default no imported fact gets your tier, not even one that was yours (`owner`) in the export: those come in at tier 1 and are listed in the result as `ownerFactsUnconfirmed` (key, value, scope), and the audit entry records them with `exportedTier: "owner"`. To confirm one, pin it as yourself (`memory.pinFact`, for example `bitterbot gateway call memory.pinFact --params '{"key":"...","value":"..."}'`). The reason: an export is a file, and a hand-edited or third-party one must not carry owner authority by accident. To keep them at your tier, opt in: `bitterbot memory import <file> --keep-owner-tier` runs a dry run, prints "This will give N facts owner authority (they will override the agent and win every conflict)" followed by how many of them replace your current owner values, and asks y/N (`--yes` skips the question; without a terminal and without `--yes` it refuses). Over the gateway, a dry run with `keepOwnerTier: true` reports `ownerTierGrants` (the count), `replacesOwnerValues` (how many replace a different value you hold at your tier) and `ownerTierGrantsHash`, a hash over the exact key, value and scope of every grant; `keepOwnerTier: true` then needs `confirmOwnerTierGrantsHash` equal to it. A missing or different hash (a file edited since the dry run, even with the same number of grants) is refused with "Dry-run again", and nothing is written. Only a key's current value is written at your tier; its history rows are written as `import`. Either way the import must be yours (admin RPC or CLI), and the audit entry records `keepOwnerTier`, `ownerTierGrants`, `ownerTierGrantsHash` and `replacesOwnerValues`. An imported fact never replaces an active fact of a higher tier (counted as `lowerTier`); against an equal or lower tier the ledger's own rules decide, and the change propagates like any other. A key the ledger does not have yet is restored with its history.
5. Values that look like credentials are refused, as the ledger refuses them from any source. A fact or preference whose value holds the export's `[redacted]` placeholder is skipped (`redacted`).
6. Capacity: facts that would become active are written only into the ledger's free room (it holds 48 active facts by default). The rest are skipped and counted as `overCapacity`, on a dry run too. An import never pushes out a fact this install already has.
7. Nothing imported outranks what was learned here: a fact's mention count is capped at 3 and its timestamps are kept between 2000-01-01 and now; a memory's importance is kept between 0 and 1; a preference's confidence is capped at 0.5 (where a newly extracted one starts). A memory marked as a `directive` comes in as `experience`, and a preference in the `identity` or `directive` category (the ones always recalled first) comes in as `personal` (both counted as `downgraded`): restate what still holds and the agent learns it again. Imported memories are marked as not first-party (`sessionTrust: "untrusted"`), so dream modes that need first-party grounding do not use them.

Imported memories are keyword-searchable at once and re-embedded in the background. Preferences have no source column; imported ones get an `import_` id. One `owner_import` audit entry records the counts. An export larger than 64 MB is refused; over the gateway the limit is lower (an RPC frame carries at most 8 MiB, parsed in one step), so use the CLI for a large one. Every decision pass pauses every 250 items so the gateway stays responsive during a large import.

## What is read-only here

- **Memories from files** (`MEMORY.md`, `memory/*.md`, skill files) are rebuilt from those files whenever they change, so a change made here would not stick. They are listed for reading; change the file instead.
- **Memories from conversations** can be forgotten (the transcript line is not edited; the memory's text is suppressed so reindexing the transcript skips it) but not edited: forget it, then pin the correct fact.
- **Frozen memories** (skills and protected core memories) cannot be changed here.

## What forgetting does not reach

- The conversation transcript a memory was learned from is still on disk; delete the conversation to remove it (and, with it, what was learned only from it).
- A forgotten passage of a conversation is matched by its exact text. If the transcript grows and the same words end up in a differently cut chunk, that chunk is indexed.
- `MEMORY.md`, scratch notes and handover briefs that repeat the forgotten text are not rewritten.
- SQLite keeps deleted text in free pages of the database file until it is compacted.

Every change is written to the memory audit log as "the owner forgot / edited this", without the text.

## Recent changes

The bottom of the Memory page lists what happened to memories lately: what you
deleted or corrected, what faded out because it was not used, what was merged
into a similar memory, and what changed while the agent was dreaming. Internal
bookkeeping is left out, and so is the text of the memory. The same list is
available from the CLI:

```bash
bitterbot gateway call memory.audit --params '{"limit": 50}'
```
